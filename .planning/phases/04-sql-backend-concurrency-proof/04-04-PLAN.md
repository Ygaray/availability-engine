<objective>
Empirically prove HOLD-02: under N genuinely concurrent, independently-connected bookers targeting a
capacity-K slot on real Postgres, at most K holds ever succeed — no overbooking under OS-level
concurrent connections, using its own dedicated real-commit, real-connection-pool fixture, never the
contract suite's per-test isolation wrapper.

This test is the actual empirical arbiter of the D-01 supersession this phase adopted: CONTEXT.md's
D-01 ("rely solely on the atomic conditional-write, defer FOR UPDATE") and the Runtime Decisions'
restated "Postgres SELECT ... FOR UPDATE" were both shown by RESEARCH.md to be theoretically unsafe
against a documented Postgres phantom-insert race; Plan 04-01 implemented the fix (a transaction-
scoped advisory lock) instead. If this test passes reliably at N >= 20 against capacity K = 1 across
multiple runs, that is the empirical confirmation the fix works; RESEARCH.md's own warning is that a
concurrency test which "usually passes" or only fails at large N is exactly the failure mode to
guard against, hence the two capacity/N combinations below rather than one.
Purpose: close out HOLD-02 and Success Criterion #3, and serve as the Phase 4 completion gate.
Output: `tests/storage/test_concurrency_proof.py`; a fully green project-wide test suite.
</objective>
