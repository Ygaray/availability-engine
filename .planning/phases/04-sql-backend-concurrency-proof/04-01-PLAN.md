<objective>
Stand up the SQL storage layer's full architecture — schema, the one dialect-locking branch
point, and a complete SQLStore implementing StorageBackend — and prove ONE real end-to-end path
(`place_hold` through SQLite) works against a genuine SQL round-trip before the phase expands to
Postgres, migrations, and the concurrency proof (Waves 2-3). This plan also implements the rest of
SQLStore's CRUD (confirm_hold/release_hold/cancel_booking) in the same pass — they are mechanical
single-row operations with no design risk, so splitting them into a later task would create a
transient Protocol-shaped-but-nonfunctional gap for no benefit — and wires the existing shared
contract suite to prove it, closing STORE-03/STORE-04 for the SQLite half of the phase.

**Supersedes CONTEXT.md's D-01.** RESEARCH.md's central finding (cited from
cybertec-postgresql.com's documented Postgres phantom-insert analysis) is that D-01's "rely solely
on the atomic `INSERT ... SELECT ... WHERE (COUNT < capacity)` conditional write" — and the Runtime
Decisions section's restated "Postgres `SELECT ... FOR UPDATE`" — are BOTH unsafe against genuinely
concurrent Postgres connections for this schema: `FOR UPDATE` cannot lock a row that does not yet
exist, so two concurrent transactions can both count zero prior holds for an empty slot and both
insert, overbooking capacity 1 to 2. The orchestrator has already ruled (per the phase brief) that
this plan adopts RESEARCH.md's portable fix instead: a Postgres transaction-scoped advisory lock
(`pg_advisory_xact_lock`, keyed on `(resource_id, slot_start)`) acquired as the first statement of
`place_hold`'s transaction, auto-released on commit/rollback. This is a schema-preserving,
`READ COMMITTED`-preserving correction (D-04's isolation level is untouched), not a new design —
`locking.py`'s module docstring records this supersession so it is auditable, and Wave 3's HOLD-02
concurrency test is the empirical arbiter of the fix.

Purpose: prove the "one SQL implementation, two dialects, one branch point" architecture works
end-to-end on the simpler dialect before paying the cost of a real Postgres container, and give
Waves 2-3 a complete, correct SQLStore to extend rather than a partial one.
Output: `src/availability_engine/storage/sql/{models,locking,store}.py`, a SQLite test-fixture
seam in `tests/storage/conftest.py`, and the existing contract suite passing for two backends.
</objective>
