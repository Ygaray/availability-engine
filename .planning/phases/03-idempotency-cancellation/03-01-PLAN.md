<objective>
**As a** network-facing consumer application integrating this engine, **I want to** cancel a
confirmed booking, **so that** its capacity reliably and immediately reappears for other bookers —
completing the write-side lifecycle this phase's HOLD-06 requirement exists for. (Phrasing derived
directly from ROADMAP.md's Phase 3 goal text and REQUIREMENTS.md's "Consumer can cancel a confirmed
Booking, freeing its capacity" — the ROADMAP `**Goal:**` line itself is prose, not literal "As a/I
want to/so that" form, so this framing is assembled from that existing text rather than invented.)

Wire `cancel_booking` end to end — contract shape, exception, Protocol declaration, storage
mutation, facade passthrough, and export — as a distinct terminal-status operation on confirmed
bookings (D-04), never routed through `release_hold`'s hold-only, silently-idempotent path.

Purpose: HOLD-06 is the simpler of this phase's two capabilities (no fingerprinting, no lock-timing
subtlety) and every layer it touches already has a direct in-repo analog (RESEARCH.md's own
conclusion) — landing it first proves the full six-file vertical slice works before Plan 03-02 adds
the more delicate idempotency-key logic on top of the same files.

Output: `BookingStatus` enum + `Booking.status` field; `BookingNotFoundError`; `cancel_booking` on
the `StorageBackend` Protocol, `InMemoryStore`, and `AvailabilityEngine`; `get_active_entries`
excluding cancelled bookings from capacity counting; full test coverage at both the facade and
storage-contract-suite level.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Consumer -> `engine.cancel_booking` | `booking_id` is caller-supplied; must resolve unambiguously to a stored, still-confirmed `Booking` or raise — never silently mutate the wrong record or no-op. |
| `storage/memory.py` (internal) -> Consumer | `BookingNotFoundError` crosses back out to the caller; must never carry the booking's opaque payload contents. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `storage/memory.py::cancel_booking` | medium | mitigate | An unknown or already-cancelled `booking_id` must be rejected (never silently no-op'd) per D-04. Implemented via explicit `.get()` + status check + raise, all inside the existing `asyncio.Lock` — deliberately NOT copying `release_hold`'s pop-and-ignore idempotent-no-op shape (Anti-Pattern in RESEARCH.md), and proven by Task 2's dedicated not-found/already-cancelled tests. |
| T-03-02 | Information Disclosure (ASVS V7) | `errors.py::BookingNotFoundError` | low | mitigate | Constructor accepts only `booking_id: str` — never the booking's payload/args — matching the module's existing no-payload-in-constructor rule (same shape as `HoldNotFoundError`, which already carries this precedent forward from Phase 1/2). |
| T-03-03 | Tampering (capacity-count integrity) | `storage/memory.py::get_active_entries` | medium | mitigate | Forgetting the CANCELLED-skip branch would let a cancelled booking silently continue occupying capacity forever, breaking HOLD-06's core guarantee. Mitigated by Task 1 extending `get_active_entries`'s existing booking loop with one `continue` branch, and verified end-to-end via `get_availability`/`place_hold` re-succeeding after cancellation (not merely a status-flag unit test) per RESEARCH.md Pitfall 4. |

</threat_model>

## Prohibition-Probe Audit

Ran the two-stage recall/precision protocol against HOLD-06. Stage 1 over-produced ~8 candidates
(silently succeeding on an already-cancelled booking, conflating a Hold id with a Booking id,
leaking the payload into an exception message, double-freeing capacity under a concurrent
double-cancel race, an implicit "un-cancel" resurrection path, a cross-resource capacity leak, an
orphaned-booking bypass, a not-found/already-cancelled enumeration oracle). Stage 2 dropped every
routine-engineering candidate (all but one are already resolved as explicit `must_haves.truths`
above, or are ordinary correctness concerns the existing lock-guarded pattern and Task 2's tests
already own — none of them are a values/safety/ethics constraint the taxonomy targets). The one
candidate that survived to a canon-referral check — the payload/booking-details-in-exception-message
concern — is canon Information Disclosure (OWASP-adjacent), already tracked as `T-03-02` in this
plan's `<threat_model>` STRIDE register rather than minted as a bespoke prohibition. The
not-found/already-cancelled enumeration-oracle candidate does not even apply here: unlike Phase 2's
`HOLD_EXPIRED`/`NOT_FOUND` split for holds, both cancellation failure modes share the single
`ReasonCode.NOT_FOUND` (Assumption A3), so there is no oracle to accept or mitigate. Zero bespoke
prohibitions kept.
