<objective>
**As a** network-facing consumer application integrating this engine, **I want to** retry
`place_hold`/`confirm_hold` safely via an idempotency key, **so that** a duplicated network retry
(the exact failure mode a network-facing caller must survive) never double-acts on the same slot —
the second, harder half of this phase's write-side-lifecycle goal, building on Plan 03-01's proven
six-file vertical slice.

Implement idempotency entirely inside `InMemoryStore`, never at the `AvailabilityEngine` facade: a
`dict[tuple[str, str], IdempotencyRecord]` keyed by `(operation_type, key)` (D-01), checked and
written inside the SAME `async with self._lock:` block that already guards `place_hold`/
`confirm_hold` — no new lock, no intervening `await` between check and store (closing the exact
TOCTOU window this codebase's own history already had to fix once for capacity checking).

Purpose: HOLD-07 is this phase's higher-risk capability — fingerprint computation and lock-critical-
section discipline are new, whereas Plan 03-01's cancellation logic was a straightforward status-flag
extension of an existing pattern. Landing it second, after the simpler vertical slice already proved
every layer wires correctly, keeps this plan's context budget focused entirely on the one genuinely
delicate mechanism the phase introduces.

Output: `IdempotencyConflictError`; `place_hold`/`confirm_hold` idempotent replay + conflict
detection on `InMemoryStore`, threaded through as a new defaulted `idempotency_key` kwarg on the
`AvailabilityEngine` facade (the Protocol already reserves it from Phase 1); a concurrency test
proving the same-key race is serialized correctly; contract-suite coverage for Phase 4 forward
compatibility.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Consumer -> `engine.place_hold`/`confirm_hold` | `idempotency_key` is an opaque, caller-supplied string; treated as untrusted data — never parsed, executed, or used to construct a path/query/format string (D-01). |
| `storage/memory.py` fingerprint computation (internal only) | The SHA-256 fingerprint hash derived from call args (`place_hold`) or `(hold_id, payload)` (`confirm_hold`) never crosses back out to the caller. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Tampering (TOCTOU) | `storage/memory.py::place_hold`/`confirm_hold` | high | mitigate | The idempotency check-execute-store sequence must happen inside the SAME `async with self._lock:` critical section with no intervening `await`, closing the exact TOCTOU window this codebase's own Phase-1 history already had to fix once for capacity checking (Pitfall 1). Mitigated by Task 1/Task 2 placing all three steps in one uninterrupted block, and proven by Task 1's dedicated concurrent-race test using `asyncio.gather`. |
| T-03-05 | Denial of Service | `storage/memory.py::_idempotency` dict | medium | accept | Unbounded idempotency-record growth from a caller minting a unique key per request — explicitly accepted risk per D-03 (dev/test in-memory backend, no reaper); the SQL retention/cleanup story is deferred to Phase 4. Adding a reaper now would violate the project's established "no background sweeper / lazy-on-read only" rule and contradict D-03. |
| T-03-06 | Information Disclosure | `errors.py::IdempotencyConflictError` | low | mitigate | Constructor accepts only `(operation_type: str, key: str)` — never the conflicting call args, payload, or the computed fingerprint hash — matching `errors.py`'s existing no-payload-in-constructor rule; the fingerprint itself is a one-way SHA-256 digest and is never surfaced in any exception message regardless. |
| T-03-07 | Tampering (failure caching) | `storage/memory.py::place_hold`/`confirm_hold` | medium | mitigate | Caching an `IdempotencyRecord` on a FAILED attempt (e.g. `CapacityExhaustedError`, `HoldExpiredError`, `HoldNotFoundError`) would permanently and incorrectly replay that failure forever, even after the underlying condition changes. Mitigated by writing the record only on the success path, strictly after the `Hold`/`Booking` is created (Pitfall 2), and proven by the "failed attempt never caches" must-have truth above. |

</threat_model>

## Prohibition-Probe Audit

Ran the two-stage recall/precision protocol against HOLD-07. Stage 1 over-produced ~9 candidates
(returning a stale/expired `Hold` unmodified on replay without re-validating its TTL; leaking the
fingerprint or payload into an exception message; unbounded idempotency-dict growth as a
memory-exhaustion DoS; a caller replaying a *different* caller's idempotency key and gaining access
to that caller's `Hold`/`Booking` result; key-scope collision misrouting a `Hold` where a `Booking`
is expected; caching a failed attempt so a legitimate later retry gets stuck; a same-key race
double-consuming capacity; treating `ttl_seconds` inconsistently between the original call and its
retry; retaining idempotency records forever with no bound). Stage 2 dropped the routine-engineering
candidates (stale-Hold-on-replay is D-02's literal, locked behavior — not a gap; key-scope collision,
failure-caching, and the same-key race are all explicit `must_haves.truths`/dedicated tests above,
not unaddressed prohibitions; `ttl_seconds` exclusion is Open Question 1's resolved design choice).
Two candidates survived to a canon-referral check and are NOT minted as bespoke prohibitions —
each is already tracked in this plan's `<threat_model>` STRIDE register instead: the
fingerprint/payload information-disclosure concern (`T-03-06`) and the unbounded-dict-growth DoS
concern (`T-03-05`, explicitly accepted per D-03). The cross-caller key-replay candidate is
**dismissed** (reason: this engine explicitly declares multi-tenancy/access-control out of scope —
RESEARCH.md's own Security Domain analysis marks ASVS V4 Access Control "no — out of scope, engine
trusts its caller for authorization" — and D-01 requires the key stay engine-opaque, never
parsed/namespaced by this library; a caller needing per-tenant isolation is expected to compose that
into its own key material before calling, which is the caller's responsibility, not this engine's).
Zero bespoke prohibitions kept.
