<objective>
Ship the thin synchronous facade (D-04) so the consumer's `AvailabilityPort` — a synchronous ABC
whose `ConversationService`/`BookingService` call it *inline* from already-running async code, per
the consumer's own `port.py` docstring — can be satisfied without crashing. A naive
`asyncio.run()`-per-call wrapper raises `RuntimeError: asyncio.run() cannot be called from a running
event loop` the first time it's invoked that way (RESEARCH.md Pitfall 3); the correct pattern is a
dedicated background thread running one persistent event loop, dispatched via
`asyncio.run_coroutine_threadsafe`.

composition root, so the consumer's one-line adapter swap works unmodified.

with a test proving the exact failure mode it exists to prevent.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer call → sync facade → background thread → engine | the facade crosses a thread boundary on every call; a consumer payload/details dict travels through `future.result()` re-raise on the error path |
| facade lifecycle → OS thread | a long-running consumer process that never calls `close()` leaks a daemon thread + event loop for the life of the process |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-05-03 | Information Disclosure | `src/availability_engine/sync.py` exception propagation path | medium | mitigate | `sync.py` performs zero exception translation or logging — engine exceptions (already payload-free per `errors.py`'s T-01-01 rule) propagate unchanged through `future.result()`; Task 1's action explicitly forbids introducing any new log/interpolation call in this module |
| T-05-04 | Denial of Service | `SyncAvailabilityEngine`'s background thread + event loop | medium | mitigate | explicit `close()` method (`loop.call_soon_threadsafe(loop.stop)` + `thread.join(timeout=5)`), proven by Task 1's Test B; daemon=True additionally prevents the thread from blocking process exit even if `close()` is never called |
</threat_model>
